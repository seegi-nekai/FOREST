# Skill: lint

Пройдись по vault или указанному полю и проверь структурную целостность: битые ссылки, дубли, осиротевшие заметки, расхождения между слоями. Идея заимствована у Карпатого (операция `lint` поверх персональной LLM-вики) и адаптирована под FOREST.

Используй инструкцию ниже, не читай другие правила-файлы во время прохода.

## Вход

По умолчанию скилл запускается без аргументов и сканирует весь vault. Опционально пользователь может передать имя поля.

## Область чтения и записи

Разрешено читать всё содержимое vault кроме `_schemas/` и `CLAUDE.md` / `AGENTS.md` (это правила, к которым lint не апеллирует).

Редактирование делится на три уровня:

1. **Auto-fix** — мелкие исправления делаются без подтверждения. Каждая правка пишется в отчёт.
2. **Ask** — вопрос пользователю, действие только после явного «да».
3. **Report** — только сообщение, действий нет.

Если в ходе работы появляется сомнение, какой уровень применить, — поднимай до «Ask».

## Шаг 0. Сбор материала

Определи область сканирования (vault целиком или одно поле). Для каждой `<field>/evergreens/`, `<field>/observations/`, `<field>/reflections/`, корневой `trails/`, `INDEX.md`:
- собери список файлов и их frontmatter;
- построй карту wiki-ссылок: откуда → куда, какие битые;
- построй карту тем-кластеров: для каждой evergreen — её ключевые понятия, теги, ссылки на evergreens других полей. На этой карте опирается детект кандидатов в тропы на шаге 2.

## Шаг 1. Auto-fix — мелкие правки без подтверждения

Применяй сразу, фиксируй в отчёт:

- **`updated:` отсутствует** на странице, у которой есть `created:` — поставь `updated: <created>`.
- **Дата в неконсистентном формате** во frontmatter — нормализуй к `YYYY-MM-DD`.
- **Trailing whitespace** и лишние пустые строки в конце файлов — удалить.
- **`type:` отсутствует во frontmatter** — поставь по принадлежности (страница в `evergreens/` → `type: evergreen` и т. п.). Если папка не FOREST-овская — пропустить.
- **Голый текст, совпадающий с именем существующей evergreen, в одной из evergreens** — заменить на wiki-ссылку `[[<имя>]]`. Только если совпадение полное (с учётом регистра и склонения — если разойдётся, поднимай до «Ask»).

## Шаг 2. Ask — спросить и сделать

По каждому обнаружению задавай вопрос отдельным сообщением:

- **Битая wiki-ссылка** на несуществующую страницу:
  > В `<file>` найдена ссылка `[[<target>]]`. Цели нет. Удалить ссылку, заменить на текст или создать заглушку-страницу?

- **Кросс-полевая ссылка на удалённое поле** (например, поле было в git у коллеги и удалено локально):
  > В `<file>` есть ссылка `[[<deleted-field>/<page>]]` на удалённое поле. Заменить на текст, оставить как есть с пометкой или удалить?

- **Вероятный дубль evergreen** — две страницы по одной идее в одном поле, формулировки близки:
  > В `<field>/evergreens/` найдены вероятные дубли: `<page-1>` и `<page-2>`. Объединить? Если да — какая остаётся как ведущая?

- **Осиротевшая evergreen** (нет входящих и исходящих wiki-ссылок, существует дольше 30 дней):
  > Страница `<file>` не связана ни с чем уже <N> дней. Удалить, перенести в `_archive/`, или это ожидаемо?

- **Empty `sources:`** на evergreen:
  > У `<file>` пустой `sources:`. Это ожидаемо (страница написана от себя) или забыли заполнить?

- **Evergreen с явно субъективным/датированным содержанием** (фразы «сейчас», «я планирую», конкретные даты):
  > В `<file>` есть текст, который выглядит как рефлексия, а не нейтральное знание: «<фрагмент>». Вынести в reflection и оставить здесь только нейтральную формулировку?

- **Reflection с нейтральной переиспользуемой формулировкой** понятия:
  > В `<file>` встретился фрагмент, который выглядит как evergreen-определение: «<фрагмент>». Вынести в `<field>/evergreens/`?

- **Источник в `observations/`, на который не ссылается ни одна evergreen**, существует дольше 7 дней:
  > Источник `<file>` лежит в `observations/` <N> дней без интеграции. Запустить process-observation для него, заархивировать или пропустить?

- **Кандидат в тропу** — кластер из 5+ кросс-полевых evergreens по близкой теме, для которого ещё нет файла в `trails/`. Детектится через комбинацию: пересекающиеся wiki-ссылки между evergreens разных полей, общие теги, семантическая близость формулировок:
  > По теме «<тема>» в полях <list> накопилось <N> кросс-полевых evergreens, тропы нет:
  > - `<field-1>/evergreens/<page-1>.md`
  > - `<field-2>/evergreens/<page-2>.md`
  > - …
  >
  > Завести тропу `trails/<имя>.md`?

## Шаг 3. Report — только перечислить

Не предлагай действий, просто включи в финальный отчёт:

- **Stale evergreens**: `updated:` старше 6 месяцев. Список с датами.
- **Одноисточниковые evergreens**: страницы со ссылкой только на один источник, существующие дольше 3 месяцев — кандидаты на консенсус (либо подкрепить, либо признать спорными).
- **Молчащие поля**: поля без активности (новых страниц, обновлений) дольше 3 месяцев.
- **Тропы без активности**: тропы, не обновлявшиеся 6+ месяцев.
- **Расхождения index ↔ файлы**: страницы, существующие на диске, но отсутствующие в `INDEX.md`; и наоборот, ссылки в индексе на несуществующие страницы.

## Шаг 4. Итоговый отчёт

Собери результат прохода в три раздела:

```
## Auto-fix (выполнено)
- <file> — что поправлено
- …

## Ask (требуют решения)
- <file> — суть вопроса, варианты
- …

## Report (к сведению)
- <тип> — <file> — деталь
- …
```

Покажи пользователю.

## Шаг 5. Логирование

Открой `log.md` в корне vault и добавь запись по конвенции из `CLAUDE.md`:

```
## [YYYY-MM-DD] lint | <scope>
```

Под заголовком:
- сколько правок auto-fix применено;
- сколько вопросов ask поднято и сколько из них решено в этом проходе;
- сколько пунктов report.

Полный отчёт целиком в лог не копируй — он избыточен; в логе только сводка и ссылка на дату прохода.

## Шаг 6. Финальная сверка

Перед завершением убедись:
- ни одна auto-fix-правка не повлияла на тело evergreens/observations/reflections в смысле содержания (только frontmatter, пробелы, замена голого текста на wiki-ссылку);
- по всем ask-обнаружениям задан явный вопрос;
- запись в `log.md` добавлена;
- отчёт показан пользователю.
